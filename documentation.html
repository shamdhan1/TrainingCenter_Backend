Detailed Breakdown: 6 Microservices

Har ek microservice ka role, port, database, aur internal components.

1. Service Registry (Netflix Eureka Server) — Port: 8761

Main Role: Phonebook of all microservices.

Jab koi service (jaise `trainer-service`) start hoti hai, to wo Eureka ke paas jaakar apna naam aur IP/Port register karwati hai ("Main live hoon!"). Jab `admin-service` ko `trainer-service` se baat karni hoti hai, to use hardcoded IP `localhost:8082` nahi likhna padta; wo Eureka se poochti hai: "TRAINER-SERVICE kahan chal rahi hai?"

Key Spring Boot Annotation: @EnableEurekaServer in ServiceRegistryApplication.java.
service-registry/src/main/resources/application.properties 
server.port=8761
eureka.instance.hostname=localhost
# Eureka ko khud ko register nahi karna padta
eureka.client.register-with-eureka=false
eureka.client.fetch-registry=false
2. API Gateway (Spring Cloud Gateway) — Port: 8080

Main Role: Single Entry Point, CORS handling, JWT Token Validation & Header Forwarding.

Frontend ko alag-alag 5 ports yaad rakhne ki jarurat nahi hai. Frontend sirf http://localhost:8080/api/v1/... par call bhejta hai. Gateway me likha hua AuthenticationFilter ye check karta hai:

  • Kya ye request open URL hai? (e.g., /api/v1/auth/login ya /actuator/health). Agar haan, to seedhe jaane deta hai.
  • Agar secured URL hai, to kya Authorization: Bearer <token> header maujood hai?
  • Kya JWT valid hai aur expire to nahi hua?
  • Token decode karke user details ko headers me inject karta hai: X-User-Id, X-User-Name, X-User-Roles taaki downstream services ko dubara token verify na karna pade!
api-gateway/src/main/resources/application.properties (Routing Rules) 
# Route 1: Auth Service
spring.cloud.gateway.routes[0].id=auth-service
spring.cloud.gateway.routes[0].uri=lb://AUTH-SERVICE
spring.cloud.gateway.routes[0].predicates[0]=Path=/api/v1/auth/**

# Route 2: Admin Service
spring.cloud.gateway.routes[1].id=admin-service
spring.cloud.gateway.routes[1].uri=lb://ADMIN-SERVICE
spring.cloud.gateway.routes[1].predicates[0]=Path=/api/v1/centers/**,/api/v1/courses/**,/api/v1/batches/**,/api/v1/dashboard/**

# Route 3: Trainer Service
spring.cloud.gateway.routes[2].id=trainer-service
spring.cloud.gateway.routes[2].uri=lb://TRAINER-SERVICE
spring.cloud.gateway.routes[2].predicates[0]=Path=/api/v1/trainers/**,/api/v1/trainer-reports/**

# Route 4: Student Service
spring.cloud.gateway.routes[3].id=student-service
spring.cloud.gateway.routes[3].uri=lb://STUDENT-SERVICE
spring.cloud.gateway.routes[3].predicates[0]=Path=/api/v1/students/**,/api/v1/admissions/**,/api/v1/enrollments/**,/api/v1/fees/**
3. Auth Service — Port: 8084 | DB: sms_auth_db

Main Role: User accounts, Passwords (BCrypt), Roles & JWT Generation.

Jab user username aur password daalta hai:

  1. AuthController.login() call hota hai.
  2. Spring Security AuthenticationManager username dhoondhta hai aur BCryptPasswordEncoder se password match karta hai.
  3. Match hone par JwtTokenProvider ek signed JWT token banata hai jisme user ID, username aur assigned roles (e.g. ROLE_ADMIN, ROLE_TRAINER, ROLE_STUDENT) embedded hote hain.
  4. Response me JWT Token aur basic profile data frontend ko return hota hai.
Tables in sms_auth_db: user_accounts (User credentials, password hash, status), roles (Role definitions), user_roles (Mapping between user & role).
4. Admin Service — Port: 8081 | DB: sms_admin_db

Main Role: Centers, Courses, Batches, aur Consolidated Dashboard Stats.

Admin Service training center system ka backbone hai:

  • Centers Management: Pune, Sambhajinagar, Ahmednagar, Mumbai, Nashik, Nagpur campuses.
  • Courses Catalog: C, C++, Core Java, Java Full Stack, Python Full Stack, Angular, Spring Microservices etc.
  • Batches Scheduling: Batch timings, start/end dates, max capacity, trainer assignment.
  • Dashboard Statistics: Admin dashboard par 4 cards dikhte hain (Total Centers, Courses, Trainers, Students). Admin service TrainerClient aur StudentClient (OpenFeign) ko call karke realtime counts aggregate karti hai!
Tables in sms_admin_db: centers, courses, course_contents, batches.
5. Trainer Service — Port: 8082 | DB: sms_trainer_db

Main Role: Trainer profiles, Trainer registration, Performance evaluations & Reports.

  • Trainer Management: Employee code, specialization, assigned center, experience.
  • Trainer Registration API: Admin jab naya trainer register karta hai to ye service trainer details persist karti hai.
  • Trainer Reports API: Trainer ke assigned students, syllabus completion %, student feedback aur attendance reports generate karta hai.
Tables in sms_trainer_db: trainers (Employee code, center_id, specialization, phone, email).
6. Student Service — Port: 8083 | DB: sms_student_db

Main Role: Student directory, Admissions, Course Enrollments, Fee Accounts & Payment Tracking.

  • Student Registration: Registration number (e.g. STU-2026-0001), personal info, guardian contact.
  • Admissions & Enrollments: Student ko kisi course aur center me enroll karna.
  • Fee Account: Total course fees, amount paid, balance amount, installments, payment receipts.
  • Academic Progress: Attendance records and assessment scores.
Tables in sms_student_db: students, enrollments, fee_accounts, payments, attendance, assessments, student_progress.

Login & Authentication Workflow

Kaise 1-click auto-login ya manual credentials se user authenticate hota hai.

Step # Actor Action Performed Internal Technical Logic
1 User / Browser Clicks "🛡️ Admin" or enters credentials Angular executes login({ username, password }) and sends POST to /api/v1/auth/login.
2 API Gateway Receives request on port 8080 Matches route /api/v1/auth/**. As it is an open route, forwards directly to lb://AUTH-SERVICE.
3 Auth Service Validates in sms_auth_db BCryptPasswordEncoder.matches(raw, hash) verifies password. Fetches roles (ROLE_ADMIN).
4 Auth Service Generates JWT Token Generates compact JWT token using JJWT library containing claims: sub: rahul_admin, roles: [ROLE_ADMIN].
5 Frontend Saves Token & Updates State Saves token in localStorage. Updates Angular Signals: currentUser.set(...) and isAdmin.set(true).
6 Router Guard Redirects to Role Dashboard Navigates to /dashboard. Angular template dynamically shows Admin View + Admin Sidebar menu!

Security Guarantee (Double Layer Protection): Even agar koi student browser me direct URL type karta hai jaise http://localhost:4200/centers, to frontend ka roleGuard.ts use detect karke wapas /dashboard bhej deta hai. Aur agar direct API call karta hai to API Gateway 403 Forbidden return karta hai.

Inter-Service Communication (Spring Cloud OpenFeign)

Kaise microservices aapas me baat karti hain bina hardcoded IP address ke.

Microservices me ek service dusri service ke database me direct SQL query nahi karti (Database-per-Service principle). Jab Admin Service ko Dashboard par "Total Trainers" aur "Total Students" dikhana hota hai, to wo OpenFeign Client use karti hai:

admin-service/.../client/TrainerClient.java 
// name = "trainer-service" Eureka me registered service ka name hai
@FeignClient(name = "trainer-service")
public interface TrainerClient {

    @GetMapping("/api/v1/trainers/count")
    ApiResponse<Long> getTrainersCount();

    @GetMapping("/api/v1/trainers/{id}")
    ApiResponse<TrainerDto> getTrainerById(@PathVariable("id") Long id);
}
Feign Ka Jadoo: Aapko sirf ek Java Interface likhna hota hai. Spring Cloud runtime par khud uska HTTP Client create kar leta hai aur Eureka se trainer-service ka IP aur Port nikaal kar request execute kar deta hai!

Database-per-Service Architecture

Har ek service ka apna independent schema aur data isolation.

Database Name Owning Service Core Tables Business Purpose
sms_auth_db Auth Service (:8084) user_accounts, roles, user_roles System access, hashed passwords, user statuses
sms_admin_db Admin Service (:8081) centers, courses, course_contents, batches Campus locations, academic curriculum, batch calendar
sms_trainer_db Trainer Service (:8082) trainers Faculty directory, specializations, ratings
sms_student_db Student Service (:8083) students, enrollments, fee_accounts, payments, attendance Student lifecycle, admissions, billing & installments
Why Database-per-Service is Mandatory in Industry: Agar sabhi services ek hi database share karengi, to jab Student Service ka table lock hoga to Admin aur Auth services bhi atak jayengi. Isolated databases hone se har service ko independent failure boundary aur scaling milti hai.

Core Concepts & Interview / Viva Q&A

Top technical questions jo exams ya job interviews me pooche jaate hain.

Q1: Monolith vs Microservices me kya antar hai, aur humne ise kyun use kiya?

Answer: Monolith me saara code (Admissions, Fees, Trainers, Auth) ek hi JAR file me hota hai. Agar Fees module me koi bug aaye to pura system down ho jata hai.

Microservices me har business domain ek independent service hoti hai jiska apna database hota hai. Agar Student Service me issue aata hai, tab bhi Admin aur Trainer services smoothly chalti rahti hain. Sath hi har service ko independently scale kiya ja sakta hai.

Q2: Eureka Server (Service Discovery) ka kya role hai?

Answer: Cloud environment me services dynamically scale hoti hain aur unka IP address change hota rahta hai. Agar hum hardcoded IP use karenge to application break ho jayegi.

Eureka ek dynamic Registry provide karta hai. Har service startup par Eureka ko apna heartbeat bhejti hai. Eureka unke live network locations ko track karta hai.

Q3: API Gateway kyun jaruri hai? Client direct microservice ko call kyun nahi karta?

Answer: Agar client (browser) direct microservices ko call karega to: 1. Browser ko 5 alag-alag ports yaad rakhne padenge. 2. Har service par alag se CORS configure karna padega. 3. Har microservice ko dubara JWT token check karna padega (code duplication). 4. Internal services public internet par expose ho jayengi jo huge security risk hai.

API Gateway ek security barrier aur router ka kaam karta hai.

Q4: JWT (JSON Web Token) Stateless Authentication kaise kaam karta hai?

Answer: Traditional session-based authentication me server memory (HttpSession) me user session save karta hai, jo microservices me scale nahi hota (kyunki request kisi bhi instance par ja sakti hai).

JWT **Stateless** hota hai: Token ke 3 parts hote hain: Header.Payload.Signature. Payload me user ka ID aur Role encrypted signature ke sath hota hai. Server ko database check kiye bina signature verify karke pata chal jata hai ki token authentic hai ya nahi.

Q5: Database-per-Service pattern me data integrity kaise maintain hoti hai?

Answer: Har service ka apna schema hota hai (e.g. `sms_admin_db`, `sms_student_db`). Kisi table par Foreign Key relation direct dusre database ke table se nahi lagaya jata. Iski jagah ID reference (e.g. `centerId`, `trainerId`) store hota hai aur detail lene ke liye REST/Feign API call use ki jaati hai.
